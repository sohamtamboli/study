Overview

How the four topics fit together, and the example store used everywhere in this cheatsheet.

Database design decides which tables exist and how they connect. SQL is the language for asking those tables questions and changing them. Postgres is the database that stores the tables and runs your SQL. Warehouse design is database design for analytics: reshaping history so big questions are fast and simple.

In JS terms: a table is an array of objects where every object has the same enforced shape. A primary key is the key prop. A foreign key is storing userId instead of nesting the user, like normalized Redux state.

OLTP vs OLAP

The same data, shaped two ways for two different jobs.

OLTP (app database)OLAP (warehouse)
JobRun the product: save this order nowAnalyze the business: revenue by month by region
Typical queryTouches a few rows by IDScans millions of rows, aggregates them
WritesConstant small inserts and updatesBulk loads, hourly or daily
ShapeNormalized (each fact in one place)Denormalized star schema (facts + dimensions)
StorageRow-orientedUsually column-oriented
ExamplesPostgres, MySQL, SQL ServerBigQuery, Snowflake, Redshift, ClickHouse
UsersYour app's backendAnalysts, dashboards, data scientists

Why not just run analytics on the app database? Heavy reports compete with real users for CPU and locks, and normalized tables need many joins for every report. Small companies often start with Postgres for both, then split once reports get slow.

SELECT basics

Read rows and choose columns.

SELECT * FROM products;                      -- every column (fine for exploring, avoid in app code)

SELECT name, price FROM products;            -- pick columns

SELECT name, price * 1.18 AS price_with_gst  -- computed column with an alias
FROM products;

SELECT DISTINCT category FROM products;      -- unique values only

SELECT name, price
FROM products
ORDER BY price DESC, name ASC                -- sort; ASC is the default
LIMIT 10 OFFSET 20;                          -- page 3 of 10 per page

In JS terms: SELECT name, price is .map(p => ({name, price})). ORDER BY is .sort(). LIMIT/OFFSET is .slice().

Large OFFSET values get slow because Postgres still reads the skipped rows. For infinite scroll, use keyset pagination: WHERE id > :last_seen_id ORDER BY id LIMIT 20.

Without ORDER BY, row order is not guaranteed, even if it looks stable.

Filtering with WHERE

Keep only rows that match a condition.

SELECT * FROM products WHERE price >= 1000;
SELECT * FROM products WHERE category <> 'Kitchen';          -- not equal (!= also works)
SELECT * FROM products WHERE category IN ('Electronics', 'Books');
SELECT * FROM products WHERE price BETWEEN 500 AND 2000;      -- inclusive both ends
SELECT * FROM customers WHERE name LIKE 'A%';                 -- starts with A, case-sensitive
SELECT * FROM customers WHERE email ILIKE '%@gmail.com';      -- case-insensitive (Postgres)
SELECT * FROM customers WHERE city IS NULL;                   -- never write = NULL

SELECT * FROM orders
WHERE status = 'paid'
  AND (created_at >= '2026-01-01' OR customer_id = 1);       -- use parentheses with OR
PatternMatches
%Any number of characters
_Exactly one character

NULL is "unknown", not empty

  • NULL = NULL is not true; it's NULL. Use IS NULL / IS NOT NULL.
  • WHERE city <> 'Pune' silently excludes rows where city is NULL.
  • COALESCE(city, 'Unknown') swaps NULL for a fallback, like JS ??.
  • IS DISTINCT FROM compares values treating NULL as a normal value.

Aggregates and GROUP BY

Collapse many rows into summary numbers.

SELECT COUNT(*) FROM orders;                    -- number of rows
SELECT COUNT(city) FROM customers;              -- non-NULL cities only
SELECT COUNT(DISTINCT city) FROM customers;     -- unique cities
SELECT SUM(price), AVG(price), MIN(price), MAX(price) FROM products;

-- one output row per category
SELECT category, COUNT(*) AS products, AVG(price) AS avg_price
FROM products
GROUP BY category;

-- HAVING filters groups (WHERE filters rows before grouping)
SELECT customer_id, COUNT(*) AS order_count
FROM orders
WHERE status = 'paid'
GROUP BY customer_id
HAVING COUNT(*) >= 3
ORDER BY order_count DESC;

-- conditional aggregates in one pass
SELECT
  COUNT(*) FILTER (WHERE status = 'paid')      AS paid,
  COUNT(*) FILTER (WHERE status = 'cancelled') AS cancelled
FROM orders;

In JS terms: GROUP BY plus SUM is reduce() into an object keyed by the group column.

Every column in SELECT must either be in GROUP BY or wrapped in an aggregate. Otherwise Postgres errors, because it can't know which row's value to show.

Joins

Combine rows from related tables using their keys.

JoinKeepsUse when
INNER JOINOnly rows with a match on both sidesYou need data from both tables
LEFT JOINAll left rows, NULLs where no match"Include customers even with zero orders"
RIGHT JOINAll right rowsRarely; rewrite as LEFT JOIN instead
FULL JOINAll rows from both sidesReconciling two lists
CROSS JOINEvery combinationGenerating grids (dates × products)
-- orders with customer names
SELECT o.id, o.created_at, c.name
FROM orders o
JOIN customers c ON c.id = o.customer_id;       -- JOIN means INNER JOIN

-- order totals: chain joins along foreign keys
SELECT o.id, c.name, SUM(oi.qty * oi.unit_price) AS total
FROM orders o
JOIN customers c    ON c.id = o.customer_id
JOIN order_items oi ON oi.order_id = o.id
GROUP BY o.id, c.name;

-- every customer and their order count, including zero
SELECT c.name, COUNT(o.id) AS orders
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
GROUP BY c.name;

-- anti-join: customers who never ordered
SELECT c.*
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.id IS NULL;

Joining a one-to-many relationship multiplies rows. If an order has 3 items, joining orders to items gives 3 rows per order. Summing an order-level column after that join counts it 3 times.

Putting a condition on the right table in WHERE turns a LEFT JOIN back into an INNER JOIN. Put it in the ON clause instead: LEFT JOIN orders o ON o.customer_id = c.id AND o.status = 'paid'.

Subqueries and CTEs

Break big queries into named, readable steps.

-- subquery in WHERE
SELECT * FROM products
WHERE price > (SELECT AVG(price) FROM products);

-- EXISTS: does at least one matching row exist?
SELECT * FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);

-- CTE (WITH): like declaring const variables before the main query
WITH order_totals AS (
  SELECT order_id, SUM(qty * unit_price) AS total
  FROM order_items
  GROUP BY order_id
),
big_orders AS (
  SELECT * FROM order_totals WHERE total > 5000
)
SELECT o.id, o.customer_id, b.total
FROM big_orders b
JOIN orders o ON o.id = b.order_id;

-- recursive CTE: walk a tree (categories with parent_id)
WITH RECURSIVE tree AS (
  SELECT id, name, parent_id, 1 AS depth FROM categories WHERE parent_id IS NULL
  UNION ALL
  SELECT c.id, c.name, c.parent_id, t.depth + 1
  FROM categories c JOIN tree t ON c.parent_id = t.id
)
SELECT * FROM tree;

Prefer CTEs for readability. Use NOT EXISTS rather than NOT IN (subquery), because NOT IN returns nothing if the subquery contains a NULL.

Window functions

Compute across related rows without collapsing them.

GROUP BY turns many rows into one. A window function keeps every row and adds a column computed over a "window" of related rows.

-- rank products by price inside each category
SELECT name, category, price,
       RANK() OVER (PARTITION BY category ORDER BY price DESC) AS price_rank
FROM products;

-- each customer's latest order (top-1 per group)
WITH ranked AS (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY created_at DESC) AS rn
  FROM orders
)
SELECT * FROM ranked WHERE rn = 1;

-- running total and day-over-day change
WITH daily AS (
  SELECT created_at::date AS day, COUNT(*) AS orders
  FROM orders GROUP BY 1
)
SELECT day, orders,
       SUM(orders) OVER (ORDER BY day)       AS running_total,
       orders - LAG(orders) OVER (ORDER BY day) AS change_vs_prev_day
FROM daily;
FunctionGives
ROW_NUMBER()1, 2, 3, 4 with no ties
RANK()1, 2, 2, 4 (gaps after ties)
DENSE_RANK()1, 2, 2, 3 (no gaps)
LAG(col) / LEAD(col)Previous / next row's value
SUM(col) OVER (...)Running or partitioned total
NTILE(4)Bucket rows into quartiles

PARTITION BY is "restart for each group". ORDER BY inside OVER is the order the window moves in.

Insert, update, delete

Change data safely.

INSERT INTO customers (name, email, city)
VALUES ('Asha', 'asha@example.com', 'Pune')
RETURNING id;                                   -- get the generated id back

INSERT INTO products (name, category, price) VALUES
  ('Keyboard', 'Electronics', 1500),
  ('Mug',      'Kitchen',      300);

UPDATE products
SET price = price * 0.9
WHERE category = 'Kitchen'
RETURNING id, price;

DELETE FROM orders WHERE status = 'cancelled' AND created_at < now() - interval '1 year';

-- upsert: insert, or update if the email already exists
INSERT INTO customers (name, email, city)
VALUES ('Asha K', 'asha@example.com', 'Mumbai')
ON CONFLICT (email) DO UPDATE
SET name = EXCLUDED.name, city = EXCLUDED.city;

-- insert only if not present
INSERT INTO customers (name, email) VALUES ('Rohan', 'rohan@example.com')
ON CONFLICT (email) DO NOTHING;

UPDATE or DELETE without WHERE affects every row. Run the same WHERE as a SELECT first, or wrap the change in a transaction so you can ROLLBACK.

ON CONFLICT needs a unique constraint or index on the conflict column. EXCLUDED refers to the row you tried to insert.

How a query runs

You write SELECT first, but Postgres logically evaluates it later.

StepClauseWhat happens
1FROM / JOINBuild the combined set of rows
2WHEREDrop rows that don't match
3GROUP BYBucket remaining rows
4HAVINGDrop buckets that don't match
5SELECTCompute output columns and aliases; window functions run here
6DISTINCTRemove duplicate output rows
7ORDER BYSort (can use SELECT aliases)
8LIMIT / OFFSETCut the result

This explains common errors. You can't use a SELECT alias in WHERE because WHERE runs first. You can't use window functions in WHERE either; wrap the query in a CTE and filter outside.

Useful functions

The ones you'll reach for weekly.

-- conditional logic, like a ternary or switch
SELECT name,
  CASE WHEN price >= 5000 THEN 'premium'
       WHEN price >= 1000 THEN 'mid'
       ELSE 'budget' END AS tier
FROM products;

-- strings
SELECT lower(email), upper(name), length(name), trim(name),
       name || ' (' || city || ')',            -- concatenate
       concat_ws(', ', city, 'India'),          -- join with separator, skips NULLs
       split_part(email, '@', 2) AS domain,
       replace(name, ' ', '-')
FROM customers;

-- dates and times
SELECT now(), current_date,
       created_at::date,                        -- cast to date
       date_trunc('month', created_at),         -- first instant of the month
       extract(year FROM created_at),
       created_at + interval '7 days',
       age(now(), created_at)
FROM orders;

-- casting and NULL handling
SELECT '42'::int, 3.7::int, price::text,
       COALESCE(city, 'Unknown'),
       NULLIF(qty, 0)                           -- returns NULL if qty = 0 (avoids divide-by-zero)
FROM customers, order_items LIMIT 1;

-- generate a series of dates (great for filling chart gaps)
SELECT generate_series('2026-01-01'::date, '2026-01-31', interval '1 day')::date AS day;

Keys

How rows are identified and how tables point at each other.

  • Primary key (PK): uniquely identifies each row. Never NULL, never duplicated. One per table.
  • Foreign key (FK): a column that must match a PK in another table. Postgres rejects orders pointing at customers that don't exist.
  • Natural key: real-world unique value, like email or PAN number. Can change, so risky as a PK.
  • Surrogate key: meaningless generated ID. The default choice for PKs.
  • Composite key: a PK made of several columns, like (order_id, product_id).
-- auto-incrementing integer (modern Postgres; prefer over SERIAL)
id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY

-- UUID: safe to generate on the client, hides row counts in URLs
id uuid PRIMARY KEY DEFAULT gen_random_uuid()

-- foreign key
customer_id bigint NOT NULL REFERENCES customers(id)
bigint identityuuid
Size8 bytes16 bytes
ReadableYes (/orders/101)No
GuessableYes, leaks volumeNo
Generate before insertNoYes

A common pattern: keep a natural key like email as UNIQUE, but use a surrogate key as the PK.

Relationships

The three shapes, and where the foreign key goes in each.

TypeExampleHow to model
One-to-manyA customer has many ordersFK on the "many" side: orders.customer_id
Many-to-manyOrders contain many products; products appear in many ordersA junction table with two FKs: order_items
One-to-oneA user has one profileFK with UNIQUE, or share the same PK
-- many-to-many: students and courses
CREATE TABLE enrollments (
  student_id bigint REFERENCES students(id),
  course_id  bigint REFERENCES courses(id),
  enrolled_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (student_id, course_id)     -- a student can't enroll twice
);

Junction tables often grow their own data. order_items stores qty and unit_price, because those belong to the pairing, not to the order or the product alone.

In JS terms: you'd never store order.products = [{...full product}] in normalized state. You'd store IDs and look them up. That's exactly what a junction table does.

Normalization

Store each fact once, so it can't get out of sync.

Without normalization, Asha's city is copied into every order. Change it in one place and the others become wrong. That's an update anomaly.

FormRuleFix when broken
1NFEach cell holds one value; no repeating columns like phone1, phone2Move the repeated values into their own table
2NFWith a composite key, every column depends on the whole keyproduct_name in order_items depends only on product_id, so move it to products
3NFColumns depend only on the key, not on other non-key columnscity → state inside customers? Split into a cities table if it matters

A memorable summary: every column depends on the key, the whole key, and nothing but the key.

When to denormalize on purpose

  • Historical snapshots: order_items.unit_price copies the price at purchase time. If the product price changes later, old orders must not change.
  • Read performance: a cached orders.total avoids summing items on every page load. You must keep it in sync.
  • Warehouses: star schemas deliberately denormalize for analytics.

Default to 3NF in your app database. Denormalize only with a specific reason you can name.

Constraints

Rules the database enforces so bad data can't get in, no matter which app writes it.

CREATE TABLE products (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  sku        text NOT NULL UNIQUE,
  name       text NOT NULL,
  price      numeric(10,2) NOT NULL CHECK (price >= 0),
  status     text NOT NULL DEFAULT 'active'
             CHECK (status IN ('active', 'archived')),
  created_at timestamptz NOT NULL DEFAULT now()
);

What happens to children when a parent is deleted

OptionEffectGood for
ON DELETE RESTRICT (default-ish)Blocks deleting a customer who has ordersImportant history like orders and payments
ON DELETE CASCADEDeleting an order deletes its itemsChildren meaningless without the parent
ON DELETE SET NULLChild keeps existing, FK becomes NULLOptional links, like assigned_to

Your frontend validation is for user experience. Constraints are for correctness. Use both: the database is the last line of defense against bugs, scripts, and race conditions.

Many apps never hard-delete important rows. Instead they add deleted_at timestamptz (soft delete) and filter it out in queries.

Naming conventions

Pick a style once and never debate it again.

  • Use snake_case for everything. Postgres folds unquoted names to lowercase, so createdAt becomes createdat.
  • Plural table names (orders) or singular (order): either works, just be consistent. Plural is more common in Postgres.
  • PK is id. FK is <singular_table>_id: customer_id.
  • Timestamps end in _at (created_at), dates in _on or _date, booleans start with is_ or has_.
  • Avoid reserved words as names: user, order, group. This is one reason plural names help.
  • Store money in the smallest unit as integer (paise) or as numeric, and name it clearly: price_paise or price with a currency column.

In JS terms: your API layer or ORM maps created_at to createdAt. Don't fight Postgres casing with quoted identifiers.

Design checklist

A repeatable process for designing a schema from a feature idea.

  1. List the nouns in the feature: customer, product, order. Each strong noun is a candidate table.
  2. Define one row of each table in a sentence: "one row is one checkout". If you can't, the table is muddled.
  3. Find relationships between each pair: one-to-many, many-to-many, or none.
  4. Place foreign keys on the "many" side; create junction tables for many-to-many.
  5. Choose types and constraints: NOT NULL by default, UNIQUE for natural keys, CHECK for allowed values.
  6. Ask what must never change (prices at purchase, addresses at shipping) and snapshot it.
  7. Write the queries your screens need and check each is straightforward.
  8. Add indexes for the columns those queries filter, join, and sort on.
  9. Add created_at and updated_at to almost everything.
  10. Draw it as an ERD (dbdiagram.io or DBeaver can generate one) and explain it to someone.

Design from your screens backward. If a page needs a query with seven joins and three subqueries, the schema may be fighting the product.

Creating tables

The full example store schema, plus how to change tables later.

CREATE TABLE customers (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name       text NOT NULL,
  email      text NOT NULL UNIQUE,
  city       text,
  created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE products (
  id       bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name     text NOT NULL,
  category text NOT NULL,
  price    numeric(10,2) NOT NULL CHECK (price >= 0)
);

CREATE TABLE orders (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id bigint NOT NULL REFERENCES customers(id),
  status      text NOT NULL DEFAULT 'pending'
              CHECK (status IN ('pending', 'paid', 'shipped', 'cancelled')),
  created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE order_items (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  order_id   bigint NOT NULL REFERENCES orders(id) ON DELETE CASCADE,
  product_id bigint NOT NULL REFERENCES products(id),
  qty        int NOT NULL CHECK (qty > 0),
  unit_price numeric(10,2) NOT NULL,
  UNIQUE (order_id, product_id)
);

CREATE INDEX ON orders (customer_id);
CREATE INDEX ON order_items (product_id);

Indexes

A sorted lookup structure that lets Postgres skip reading the whole table.

In JS terms: scanning a table is array.find(). An index is building a Map keyed by that column. Lookups become fast, but every insert must update the Map too.

CREATE INDEX orders_customer_id_idx ON orders (customer_id);

-- composite: helps WHERE customer_id = ? ORDER BY created_at DESC
CREATE INDEX ON orders (customer_id, created_at DESC);

-- unique index doubles as a constraint
CREATE UNIQUE INDEX ON customers (lower(email));     -- expression index

-- partial: index only the rows you query
CREATE INDEX ON orders (created_at) WHERE status = 'pending';

-- jsonb / arrays / full-text search
CREATE INDEX ON events USING gin (payload);

-- build without locking writes on a live table
CREATE INDEX CONCURRENTLY orders_status_idx ON orders (status);

Rules of thumb

  • Primary keys and UNIQUE columns get an index automatically. Foreign keys do not; index them yourself.
  • Index columns used in WHERE, JOIN ... ON, and ORDER BY of frequent queries.
  • Composite index column order matters: (a, b) helps queries on a or a and b, not on b alone.
  • Low-variety columns (a boolean, a 3-value status) rarely benefit, except as partial indexes.
  • Wrapping a column in a function (WHERE lower(email) = ...) skips a plain index; use an expression index.
  • LIKE 'abc%' can use an index; LIKE '%abc' can't.
  • Each index slows writes and uses disk. Add them for real queries, then verify with EXPLAIN.

Reading it

  • Read from the most indented line outward; inner nodes run first.
  • Compare estimated rows with actual rows. Big mismatches mean stale statistics: run ANALYZE tablename;.
  • Find the node with the largest actual time. That's your bottleneck.
  • Paste plans into explain.dalibo.com or explain.depesz.com for a visual breakdown.

The N+1 problem: fetching 50 orders, then running one query per order for its items, is 51 round trips. Use one JOIN, or one WHERE order_id = ANY($1) query. This is the most common slowdown in apps built with ORMs.

Transactions

Group statements so they all succeed or all fail.

BEGIN;
  INSERT INTO orders (customer_id, status) VALUES (1, 'paid') RETURNING id;   -- say it returns 7
  INSERT INTO order_items (order_id, product_id, qty, unit_price) VALUES (7, 2, 1, 300);
  UPDATE inventory SET stock = stock - 1 WHERE product_id = 2;
COMMIT;       -- or ROLLBACK; to undo everything since BEGIN
ACIDGuarantee
AtomicityAll statements apply, or none do
ConsistencyConstraints hold before and after
IsolationConcurrent transactions don't see each other's half-done work
DurabilityOnce committed, it survives a crash

Isolation levels in Postgres

  • Read committed (default): each statement sees data committed before it started.
  • Repeatable read: the whole transaction sees one consistent snapshot.
  • Serializable: behaves as if transactions ran one at a time; may fail and need a retry.
-- avoid lost updates when two requests change the same row
BEGIN;
SELECT stock FROM inventory WHERE product_id = 2 FOR UPDATE;   -- locks the row
UPDATE inventory SET stock = stock - 1 WHERE product_id = 2;
COMMIT;

-- or do it atomically in one statement
UPDATE inventory SET stock = stock - 1
WHERE product_id = 2 AND stock > 0
RETURNING stock;

Keep transactions short. Never wait for user input or call a slow external API while one is open; it holds locks.

JSONB

Store and query JSON inside Postgres, for data that's truly flexible.

CREATE TABLE events (
  id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  type    text NOT NULL,
  payload jsonb NOT NULL,
  at      timestamptz NOT NULL DEFAULT now()
);

INSERT INTO events (type, payload)
VALUES ('click', '{"button": "buy", "page": "/p/42", "meta": {"ab": "B"}}');

SELECT payload -> 'meta'          AS meta_json,   -- returns jsonb
       payload ->> 'button'       AS button,      -- returns text
       payload #>> '{meta,ab}'    AS variant      -- nested path as text
FROM events;

SELECT * FROM events WHERE payload @> '{"button": "buy"}';   -- contains (GIN-indexable)
SELECT * FROM events WHERE payload ? 'meta';                 -- key exists

UPDATE events SET payload = jsonb_set(payload, '{button}', '"checkout"') WHERE id = 1;

-- build JSON for your API directly in SQL
SELECT jsonb_build_object('id', o.id, 'items', jsonb_agg(oi.*)) AS order_json
FROM orders o JOIN order_items oi ON oi.order_id = o.id
GROUP BY o.id;

Use JSONB for truly variable data: event payloads, third-party webhooks, user settings. If you filter, join, or constrain a field regularly, make it a real column.

Views

Save a query under a name and query it like a table.

-- a view re-runs its query every time
CREATE VIEW order_totals AS
SELECT o.id, o.customer_id, o.created_at, SUM(oi.qty * oi.unit_price) AS total
FROM orders o JOIN order_items oi ON oi.order_id = o.id
GROUP BY o.id;

SELECT * FROM order_totals WHERE total > 1000;

-- a materialized view stores the result; refresh it on a schedule
CREATE MATERIALIZED VIEW monthly_revenue AS
SELECT date_trunc('month', created_at) AS month, SUM(total) AS revenue
FROM order_totals GROUP BY 1;

REFRESH MATERIALIZED VIEW monthly_revenue;

In JS terms: a view is a getter that recomputes on every access. A materialized view is a memoized value you invalidate manually.

Using Postgres from your app

What changes when the SQL comes from your Node backend.

// node-postgres (pg)
import pg from 'pg';
const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL });

// ALWAYS use placeholders; never build SQL with template strings
const { rows } = await pool.query(
  'SELECT id, name FROM customers WHERE email = $1',
  [email]
);

SQL injection: `... WHERE email = '${email}'` lets a user type ' OR 1=1 -- and read everything. Parameterized queries ($1) send data separately from SQL, so it can never become code.

  • Connection string: postgres://user:password@host:5432/dbname
  • Pooling: opening connections is expensive. Use a pool; on serverless, use PgBouncer or your host's pooler.
  • ORMs and query builders: Prisma, Drizzle, Kysely, TypeORM, Sequelize. Learn the SQL anyway; you'll need it to debug them.
  • Migrations: every schema change is a versioned file checked into git and run in order.
  • Hosted Postgres: Supabase, Neon, AWS RDS, Google Cloud SQL, Render, Railway.
  • Least privilege: your app's database user shouldn't be a superuser.

Facts and dimensions

The two kinds of tables in a warehouse.

Fact tableDimension table
HoldsEvents and measurementsDescriptive context
AnswersHow much, how manyWho, what, where, when
ColumnsForeign keys + numeric measuresKey + many text attributes
SizeVery tall (millions to billions of rows)Short and wide
Examplefact_sales: date_key, product_key, customer_key, qty, revenuedim_product: product_key, name, category, brand

Grain: decide this first

The grain is what one fact row represents. "One row per order line item" is a different table from "one row per order" or "one row per product per day". Mixing grains in one table causes double counting.

Choose the most detailed grain you can afford. You can always roll line items up into daily totals, but you can never split daily totals back into line items.

Kinds of measures

  • Additive: can be summed across every dimension: revenue, qty.
  • Semi-additive: summable across some dimensions but not time: account balance, stock level.
  • Non-additive: never summed: ratios and percentages. Store the parts (numerator, denominator) instead.

Date dimension

CREATE TABLE dim_date AS
SELECT to_char(d, 'YYYYMMDD')::int AS date_key,
       d::date                      AS full_date,
       extract(year FROM d)::int    AS year,
       extract(quarter FROM d)::int AS quarter,
       to_char(d, 'YYYY-MM')        AS year_month,
       to_char(d, 'Day')            AS weekday,
       extract(isodow FROM d) IN (6, 7) AS is_weekend
FROM generate_series('2020-01-01'::date, '2030-12-31', interval '1 day') d;

A date dimension makes "weekends vs weekdays" or "fiscal quarter" a simple join instead of date math in every query. Add holidays and fiscal periods as columns.

-- the classic star query: filter and group by dimensions, sum facts
SELECT d.year_month, p.category, c.city,
       SUM(f.revenue) AS revenue, SUM(f.qty) AS units
FROM fact_sales f
JOIN dim_date d     ON d.date_key = f.date_key
JOIN dim_product p  ON p.product_key = f.product_key
JOIN dim_customer c ON c.customer_key = f.customer_key
WHERE d.year = 2026
GROUP BY 1, 2, 3
ORDER BY 1, revenue DESC;

Modern columnar warehouses also make "one big table" (fact and dimension columns pre-joined) a reasonable choice for specific dashboards.

Slowly changing dimensions

What to do when a dimension's attributes change over time.

Asha moves from Pune to Mumbai. Should last year's sales count toward Pune or Mumbai? Your answer picks the SCD type.

TypeBehaviorResult
Type 0Never change the valueOriginal value kept forever
Type 1OverwriteAll history now shows Mumbai. Simple, loses history.
Type 2Add a new row with validity datesOld sales stay Pune, new sales are Mumbai. Most common for important attributes.
Type 3Add a previous_city columnKeeps one level of history
-- Type 2 dimension
CREATE TABLE dim_customer (
  customer_key bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,  -- surrogate, new per version
  customer_id  bigint NOT NULL,                                  -- natural ID from the app
  name         text,
  city         text,
  valid_from   date NOT NULL,
  valid_to     date NOT NULL DEFAULT '9999-12-31',
  is_current   boolean NOT NULL DEFAULT true
);
-- customer_key | customer_id | city   | valid_from | valid_to   | is_current
-- 1            | 1           | Pune   | 2024-01-10 | 2026-08-31 | false
-- 7            | 1           | Mumbai | 2026-09-01 | 9999-12-31 | true

Facts store customer_key, so each sale permanently points to the version that was true when it happened. That's why warehouse dimensions use their own surrogate keys instead of the app's IDs.

Typical modern layers

  1. Raw / staging: exact copies of source tables, lightly cleaned (renamed columns, fixed types).
  2. Intermediate: joins and business logic, like "an order counts as revenue once paid".

Loading strategies

  • Full refresh: reload everything. Simple; fine for small tables.
  • Incremental: only rows where updated_at is newer than the last run. Needs reliable timestamps.
  • Change data capture: stream inserts, updates, and deletes from Postgres's write-ahead log.

Make loads idempotent: running the same job twice should give the same result, not duplicate rows. Delete-then-insert by date range, or merge on keys.

Why columnar is fast

The storage idea behind every modern warehouse.

Row store (Postgres):     [1, Asha, Pune, 2100] [2, Rohan, Mumbai, 9000] ...
Column store (warehouse): id: [1, 2, ...]   name: [Asha, Rohan, ...]   total: [2100, 9000, ...]
  • SUM(total) reads only the total column, not whole rows.
  • Similar values sit together and compress extremely well.
  • Single-row lookups and updates get slower, which warehouses don't need much.

Warehouse cost tips: select only the columns you need (SELECT * can be expensive on BigQuery), and filter on partition columns, usually date, so whole chunks get skipped.

In JS terms: a row store is an array of objects. A column store is an object of arrays, like { id: [...], total: [...] }, which is how charting libraries often want data anyway.

Analytics SQL patterns

Queries you'll write over and over in a warehouse.

-- monthly revenue with month-over-month growth
WITH m AS (
  SELECT date_trunc('month', order_date) AS month, SUM(revenue) AS revenue
  FROM fact_sales GROUP BY 1
)
SELECT month, revenue,
       round(100.0 * (revenue - LAG(revenue) OVER (ORDER BY month))
             / NULLIF(LAG(revenue) OVER (ORDER BY month), 0), 1) AS growth_pct
FROM m ORDER BY month;

-- share of total
SELECT category, SUM(revenue) AS revenue,
       round(100.0 * SUM(revenue) / SUM(SUM(revenue)) OVER (), 1) AS pct_of_total
FROM fact_sales f JOIN dim_product p USING (product_key)
GROUP BY category;

-- cohort: customers grouped by first-purchase month, active in later months
WITH firsts AS (
  SELECT customer_id, date_trunc('month', MIN(order_date)) AS cohort
  FROM fact_sales GROUP BY 1
),
activity AS (
  SELECT DISTINCT customer_id, date_trunc('month', order_date) AS month
  FROM fact_sales
)
SELECT f.cohort, a.month, COUNT(*) AS active_customers
FROM firsts f JOIN activity a USING (customer_id)
GROUP BY 1, 2 ORDER BY 1, 2;

-- 7-day moving average
SELECT day, revenue,
       AVG(revenue) OVER (ORDER BY day ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) AS ma_7d
FROM daily_revenue;

-- pivot with conditional aggregation
SELECT p.category,
       SUM(revenue) FILTER (WHERE d.quarter = 1) AS q1,
       SUM(revenue) FILTER (WHERE d.quarter = 2) AS q2,
       SUM(revenue) FILTER (WHERE d.quarter = 3) AS q3,
       SUM(revenue) FILTER (WHERE d.quarter = 4) AS q4
FROM fact_sales f
JOIN dim_product p USING (product_key)
JOIN dim_date d USING (date_key)
GROUP BY p.category;

Multiply by 100.0, not 100: integer division in SQL drops decimals, so 1 / 4 is 0.

Warehouse design checklist

The Kimball four-step process, plus practical checks.

  1. Pick the business process: sales, signups, support tickets. One fact table per process.
  2. Declare the grain: "one row per order line item". Write it down.
  3. Identify dimensions: who, what, where, when, how. Each becomes a dim table.
  4. Identify facts: the numeric measures at that grain.
  • Every fact row has a valid key for every dimension. Use an "Unknown" member row instead of NULL keys.
  • Decide the SCD type for each important dimension attribute.
  • Store monetary facts in one currency or alongside a currency column.
  • Write tests: row counts match the source, keys are unique, no NULL foreign keys (dbt tests do this).
  • Document every column's meaning. "Revenue" means different things to finance and marketing.
  • Partition big fact tables by date.

The book that defined this field is The Data Warehouse Toolkit by Ralph Kimball and Margy Ross. Chapters 1 to 3 cover most of what you'll use.
